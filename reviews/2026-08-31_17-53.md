## Executive verdict

Junoview has moved substantially since the 30 August reports. Thirty-three
commits landed on `main` during or since that review window. The former P0 wheel
packaging defect, non-notebook source doors, source-relative figures, Markdown
and LaTeX fidelity, fullscreen isolation, alt text, links/actions, PowerPoint
notes/crops/transitions/tables, stale-write protection, review export, talk
controls, and several missing UI doors have all been addressed.

The clean committed snapshot is healthy at the automated-gate level: **908
tests pass**, Ruff is clean, mypy is clean, and the built-in self-test succeeds.
A live browser pass also booted the app and editor without console errors.

That does not mean the feature surface is complete. The review found:

1. A source-refresh command can silently fail to read the disk and then tell
   the user that every figure matches its source.
2. A presentation with no notebook references loses its visible way back to
   the notebooks, even though the empty-state copy tells the user to go there.
3. The new overview says “Every object” but deliberately prevents arrows from
   being moved there.
4. Layout Ideas was marked done with a recorded cut: built-in templates are not
   included in the preview chooser requested by the task.
5. The new range parser can store out-of-bounds ranges after swapping reversed
   endpoints.
6. “Self-contained” HTML still reaches Google Fonts and can change typography
   offline or under network/privacy blocking.
7. The largest product gaps remain native data-bound charts, an authored
   reading order (being implemented while this report was written), workbook
   support, PowerPoint import/round-trip, true masters, media, and richer Office
   export semantics.

The first two findings should be fixed before treating the current batch as
finished. The platform should then prioritise the notebook-first “and more”
feature already selected in `TASKS.md`: native, provenance-bound charts.

## Findings

### JVR-01 — “Update figures” can report success after failing to read disk

**Priority:** P1  
**Type:** correctness / provenance / incomplete failure handling  
**Confidence:** high; direct control-flow evidence

The command is presented as one reliable verb that reaches the source file.
That promise is not upheld on I/O, parse, route, or other reload failures.

Evidence:

- `src/junoview/assets/js/app.js:5288-5296`, `APP.reloadTab(stem)`, calls
  `/api/open`, but its final `catch(function(){return false;})` erases every
  error and returns the same `false` used for an intentionally unsupported URL
  source.
- `src/junoview/assets/js/deck/35-arranging.js:1986-2016`,
  `resyncAllFigures()`, waits for the booleans, counts truthy reloads, and then
  **always** runs `staleFigures()` against the shell currently in memory.
- If the source file was deleted, became unreadable, or now fails to parse, the
  old in-memory shell remains. If that cached shell matches the saved figure,
  the command says `Every figure on this deck already matches its source`.
- In a mixed run, one source can reload and another can fail; the success toast
  reports only the successful re-read count and never names the failure.
- `tests/test_provenance.py:254-311` pins the function and success wiring with
  substring assertions. It does not exercise a rejected `/api/open`, a mixed
  result, a missing file, or the text of the resulting toast.

Why it matters: provenance is one of Junoview’s differentiating features. A
false “matches its source” statement is worse than a visible refresh failure,
because the user may present or export stale scientific output believing the
disk was checked.

Suggested implementation boundary:

- make `APP.reloadTab` return a structured result such as
  `{stem, ok, reason}` or reject with the source stem preserved;
- distinguish `unsupported URL` from `failed to re-read local file`;
- do not emit an all-current success message when any referenced local source
  failed to reload;
- list failed source names and keep stale/current claims limited to the sources
  actually read;
- add a behavioural JS test for all-success, all-failure, and mixed results.

Minimal reproduction:

1. Open a notebook and make a deck figure from one of its cards.
2. Save the deck, then delete, rename, corrupt, or make the notebook unreadable.
3. Use **File → Update figures from their sources**.
4. Observe that the reload error is swallowed and the cached shell can support
   the false “already matches” toast.

### JVR-02 — an empty-reference deck loses its visible route back to notebooks

**Priority:** P1  
**Type:** navigation / empty-state bug / awkward layout  
**Confidence:** high; source evidence plus live browser reproduction

The left notebook column is documented in code as the way back to the notebook
surface. In the exact state where a user most needs that route—an empty or
standalone presentation—it disappears.

Evidence:

- `src/junoview/assets/js/deck/55-sections-and-strip.js:728-734`,
  `buildNbsInto(m, column)`, calculates `nbInfo()` and returns immediately when
  it is empty.
- The early return inserts only: `No notebooks yet — add cells from your
  notebooks to a slide.`
- The clickable `↩ notebooks` header is created only after that return at
  `55-sections-and-strip.js:735-739`; its click handler calls `closeDeck()`.
- The comment at `55-sections-and-strip.js:741-742` explicitly calls this
  header “the way back on the left”.
- `tests/test_decks.py:204` checks only that `buildNbsInto($('#dc-nbs'),true)`
  is present. No test contains the `No notebooks yet` state or asserts that a
  return control survives it.
- Live browser reproduction: open the example app, then open the existing
  presentation with no referenced notebook frames. The left column contained
  only the empty message. It contained no Notebooks/back control. The File menu
  also offered no visible Close command. `Esc` still works, but the UI neither
  shows nor teaches that hidden escape route.

Why it matters: the text asks the user to add notebook cells while removing the
only nearby door to the notebooks. This is a classic empty-state dead end and
makes a new deck feel like a separate app with no way home.

Suggested fix: construct and append the column header before checking
`info.length`; put the empty message in the body below it. Add a DOM-level test
that calls the empty branch in column mode and proves the `closeDeck()` control
exists and is keyboard operable. A worded **Close presentation** item in File
would provide a second discoverable route without adding ribbon width.

### JVR-03 — “Every object” overview excludes arrows from moving

**Priority:** P2  
**Type:** recently completed feature is partial  
**Confidence:** high; explicit exclusion

T130 is marked done and its UI section is headed **Every object, outlined**.
The implementation draws arrows in the miniature but does not create the drag
proxy that makes an object movable from the overview.

Evidence:

- `src/junoview/assets/js/deck/50-review-and-overview.js:2032-2036` uses the
  literal heading `Every object, outlined`.
- The proxy comment at `:2061-2067` says “One drag proxy per object” and even
  says `shiftAnnot` lets “an arrow move by its endpoints”.
- The next line, `:2069`, is
  `if(!a||a.hide||a.k==='arrow') return;`, so arrows never receive that proxy.
- `miniDiagram()` separately renders arrows through SVG at approximately
  `:2176` and `:2259-2271`; this is not a rendering limitation.
- `tests/test_style_sets.py:323-327` asserts only that `.dg-drag` exists and is
  displayed in outline mode. It does not require one proxy per supported item
  kind or exercise an arrow drag.

Suggested fix: compute an arrow proxy from the bounding box of its endpoints;
on drag use `shiftAnnot`, as the comment already intends. Give very thin or
zero-length lines a minimum hit target without changing their visible bounds.
Add a test fixture containing every `ANNOT_KINDS` entry and assert the supported
overview action for each one.

### JVR-05 — reversed range input can escape the slide bounds

**Priority:** P3  
**Type:** edge-case logic bug  
**Confidence:** high; arithmetic proof

The new design-surface scope parser at
`src/junoview/assets/js/deck/50-review-and-overview.js:1753-1763` clamps the
first endpoint only on the lower side and the second endpoint only on the upper
side, then swaps them if reversed:

```js
sc.from = Math.max(1, first);
sc.to = Math.min(total, second);
if (sc.to < sc.from) swap();
```

For a ten-slide deck, input `999-1` becomes `from=999, to=1`, then swaps to
`from=1, to=999`. The selected slides happen to remain the existing slides, but
the stored range violates the promised `1..total` invariant and can produce
misleading labels/state. Other reversed out-of-range combinations similarly
clamp the wrong endpoint.

Suggested fix: parse both raw endpoints, sort them, then clamp **both** sorted
values into `1..total`. Add cases for `9-3`, `999-1`, `20-15`, `0-0`, and a
single number above the deck length.

### JVR-06 — “self-contained” output still depends on Google Fonts

**Priority:** P2 for portability/style consistency; P3 for functionality  
**Type:** product claim / offline visual fidelity / privacy edge  
**Confidence:** high for the request; moderate for user impact because fallback
fonts keep the page usable

Evidence:

- `README.md:133` calls the static page “shareable, self-contained”.
- `src/junoview/assets/css/core.css:2` imports IBM Plex families from
  `https://fonts.googleapis.com`.
- `src/junoview/assets/js/widget.js:17` injects the same external stylesheet.
- `src/junoview/assets/js/sw.js:28-40` precaches Pyodide, MathJax, Plotly, and
  the example, but not the IBM Plex stylesheet/font files.
- The service worker allows Google font hosts at `sw.js:61-65` and caches only
  `res.ok` responses at `:114-116`. This is opportunistic runtime caching, not
  deterministic inclusion in the exported HTML.
- A `file://` static export has no service-worker protection at all; offline,
  blocked, or privacy-restricted Google requests fall back to local fonts.

The document content still renders, but metrics and line wrapping can change.
That matters to a presentation/poster tool: a title fitting online may wrap on
an offline presentation machine.

Suggested resolution: either bundle/subset the licensed font assets into the
rendered document/web cache, or change the claim to “single HTML file; external
fonts are optional” and deliberately test the fallback typography. A strict
byte-stable/self-contained mode should make no network requests.

## Missing and partial capability map

The following are product gaps, not all immediate bugs. “Missing” is based on
exhaustive registries and explicit backlog decisions rather than a casual text
search.

### 1. Native, data-bound charts — highest-value missing feature

**Status:** absent; open T117  
**Recommended priority:** next major design task

Evidence:

- `src/junoview/notebook/deck_schema.py:207-219` exhaustively defines the item
  kinds: text, cell, rect, image, arrow, draw, table, and flip. There is no
  chart/series/data-binding item.
- `DECK-FORMAT.md` mirrors the same registry.
- Figures are notebook card snapshots or images. The PowerPoint writer emits a
  picture, so series cannot be recoloured or edited in PowerPoint.
- `TASKS.md:2112-2119` identifies the existing Plotly-spec seam and proposes a
  notebook-anchor binding plus a small declarative chart schema.
- `TASKS.md:2394-2398` explicitly ranks T117 first under the chosen
  “notebook-first, deepened” direction.

Best Junoview-shaped version: a durable object linked to a notebook anchor,
holding a small chart grammar and a cached preview, with provenance/staleness,
accessible description, native editing, and a real PowerPoint chart export.
This is more differentiated than copying Excel’s chart dialog.

### 2. Authorable reading order and accessibility checking

**Status:** T106 actively in progress during this review; not yet accepted  
**Recommended priority:** finish and verify before adding more object kinds

The committed snapshot uses `orderedIdx()`’s top/left heuristic for builds,
figure numbering, matching, and review output. `TASKS.md:1982-1988` correctly
states that an override needs a durable key and one resolver shared by all six
consumers. The in-progress diff is taking that route with slide-level `rord`
and stable annotation `oid`s.

Finishing T106 is necessary but not the complete accessibility story. Still
needed after it:

- a review lint for unnamed/decorative-vs-informative objects;
- contrast checks using actual foreground/background tokens;
- table header semantics beyond visual `thead` styling;
- media caption checks once media exists;
- validation that exported PowerPoint/PDF/HTML preserve the intended semantics,
  not merely the editor’s ordering UI.

### 3. Excel/workbook support

**Status:** deliberately absent; open design T113  
**Recommended priority:** strategic decision after chart/read-order work

Evidence:

- `src/junoview/notebook/sources.py:21-29` explicitly excludes `.xlsx` and
  calls CSV the limited “Excel half”.
- `sources.py:761-772`, the exhaustive `SOURCES` registry, contains only
  notebook, Markdown/Quarto, LaTeX, CSV, and TSV producers.
- `tests/test_sources.py:239` deliberately asserts
  `source_label("x.xlsx") == ""`.
- Every current producer is text-oriented. `.xlsx` is a ZIP package of XML and
  binary relationships, so loader/web bridges need a bytes seam first.

CSV preview is not a spreadsheet. A credible workbook scope would need, at
minimum, multiple sheets, cell types/formulas and cached values, ranges/tables,
formatting, merged cells, charts, named ranges, and an explicit policy for
calculation. PivotTables, Power Query, macros, external connections, and full
Excel calculation are separate decisions.

Do not add `.xlsx` as another shallow `sources.py` text parser. Choose one:

- read-only workbook ingestion with explicit loss reporting;
- optional local dependency with web-mode limitations;
- a stdlib ZIP/XML reader for a deliberately small subset;
- or state plainly that Junoview integrates notebook/CSV data and is not a
  workbook editor.

### 4. PowerPoint import and round-trip

**Status:** absent; open design T114

Evidence:

- `src/junoview/assets/js/pptx.js` is an export writer, not an importer.
- The only deck import accepts Junoview JSON/polyglot HTML.
- `.pptx` is not in `SOURCES`, and a presentation import should produce a deck,
  not the `Document` returned by source producers.
- `TASKS.md:2083-2091` records the format-boundary mismatch and requires a loss
  report rather than a false round-trip claim.

Start with a read-only import spike for common text boxes, pictures, simple
shapes, tables, slide size, notes, and basic themes. Preserve unknown OOXML
parts or report them; never silently claim fidelity for macros, SmartArt,
embedded workbooks, media, or animation.

### 5. True masters and inherited layouts

**Status:** partial/absent; open design T115

Current layouts stamp geometry into independent annotations. The deck’s `lay`
field is only the id of the last applied template, not a live inheritance link.
`pptx.js:734-780` writes one slide layout and one slide master; slide objects
still carry direct formatting.

Real masters require template identity, placeholder identity, inherited theme
properties, per-slide overrides, and migrations for flattened decks. Do not
confuse this with linked components: components reuse content; masters inherit
roles and formatting.

### 6. Equations, animation builds, and richer PowerPoint semantics

**Status:** partial; open T110

Small export wins have landed: notes, crops, transitions, links/actions, tables,
and real package-byte tests. The remaining items are architectural:

- equations are flattened through `texPlain`; there is no parse tree from
  which to create editable OMML;
- Junoview entrance builds and flip books are not exported as PowerPoint timing
  graphs;
- master/placeholder inheritance is absent as above;
- unsupported writer objects end at `pptx.js:676-706` in `skipped++`, so the
  loss report remains essential.

### 7. Native audio/video, recording, and captions

**Status:** absent as a deck object; open design T116

Evidence:

- the exhaustive annotation kinds contain no media item;
- `src/junoview/assets/html/deck.html:959` and `:963` accept `image/*` only;
- stored notebook `<video>` output can display inside a card, but there is no
  media insert door, timeline, poster frame, caption track, storage policy, or
  media-aware export.

Design storage before UI: recordings are much larger than the images that
already required IndexedDB handling. Treat captions/transcripts and alt
semantics as durable model fields, not exporter afterthoughts.

### 8. Hosted accounts, coauthoring, and live audience features

**Status:** intentionally cut/local architecture boundary; open design T119

The local server correctly binds localhost and token-guards mutations. Real
coauthoring, comments, presence, share links, polls, cloud recording, and live
captions require identity, tenancy, conflict resolution, retention, abuse
controls, and a security review. They should not be grown by exposing the local
file server route by route.

The shipped single-user collaboration substitutes—history, branches, diff,
review report, and comments/notes—are valuable, but should not be described as
real-time coauthoring.

### 9. Extension/add-in model

**Status:** absent; open design T120

New source types require Python registry and UI-gate edits. New object kinds
touch the schema, normaliser, assembled IIFE, clipboard, history, rendering,
and exporters. `SOURCES` is the nearest real plugin seam; `deck_api.py` is the
automation seam. Any extension design must preserve no-build-step `file://`
operation and stdlib-only/Pyodide core constraints.

### 10. Multi-language pasted-code highlighting

**Status:** explicit accepted cut from T128

`TASKS.md:2318-2327` records that plain prose paste and a plain-text escape now
work, while **Python-only highlighting is accepted and not fixed**. If Junoview
is intended for broad scientific/technical use, language detection or an
explicit language selector remains a legitimate follow-up. Keep plain paste as
the guaranteed escape when detection is uncertain.

### 11. Built-in template recommendations

**Status:** partial; T131 scope cut

As recorded in JVR-04, layout previews cover tidy presets and saved
arrangements, not built-in templates. Completing this would make the current
feature read as one coherent “show me good options for this content” surface
instead of two adjacent systems.

## UI and style review

The live pass did **not** find a broad regression in the user-confirmed ribbon
style. Buttons in the inspected editor and Talk panel remained words plus icons,
and the ribbon did not wrap. The Talk settings panel exposed global, headings,
body, and caption build controls in a compact, understandable layout. No browser
console warnings or errors appeared during app boot, tour dismissal,
presentation opening, or Talk-panel use.

The main style/usability issues found are therefore specific rather than a call
for another redesign:

- fix the empty-reference navigation dead end (JVR-02);
- make “Every object” literally cover arrows or rename the promise (JVR-03);
- consolidate all layout recommendations into the same preview experience
  (JVR-04);
- preserve typography without a network dependency, or state the fallback
  honestly (JVR-06).

Avoid replacing labels with icon-only controls: `AGENTS.md` explicitly records
that icon-only ribbon buttons were rejected twice.

## Recommended handoff order

1. **Finish and independently verify the active T106 work.** It owns central
   schema/ordering/editor files and must not overlap another deck.js session.
2. **Fix JVR-01.** Failed source refreshes must never produce a clean/current
   provenance claim.
3. **Fix JVR-02.** Preserve the visible Notebooks/Close route in the zero-ref
   empty state and add a behavioural test.
4. **Close T130’s arrow hole and range edge** (JVR-03/JVR-05) in one narrowly
   scoped overview follow-up with real interaction tests.
5. **Choose the next major product task: T117 native provenance-bound charts.**
   Define the durable schema and export loss policy before UI work.
6. **Then decide the bytes boundary shared by T113 workbook ingestion and T114
   PowerPoint import.** Do not build either on the current text-only producer
   seam.
7. Track template recommendations, packaged fonts/honest self-contained copy,
   media, masters, and richer PowerPoint semantics as explicit follow-ups rather
   than silently folding them into unrelated ribbon work.

For every “done” task, require three kinds of evidence in its `TASKS.md` note:

- a model/schema or source-level test for durable behaviour;
- a failure/edge test, not only a success substring assertion;
- a live drive for the user-facing gesture and the exact feedback text.

That combination would have caught both of this review’s P1 findings before the
tasks were declared complete.
