# Junoview interaction and control-design review

**Reviewed:** 2026-08-31 23:07 BST  
**Committed snapshot:** 147c4ff (main, identical to origin/main)  
**Previous review:** reviews/2026-08-31_18-52.md  
**Purpose:** review how Junoview's implemented features are exposed and used,
identify controls that are confusing or mechanically broken, and specify a
more natural interaction model for the whole product.

This is an evidence report, not a product-code change. The only file created by
this review is this report.

## Executive verdict

Junoview has a lot of real capability, but it does not yet have one coherent
way of operating that capability. The central problem is not simply that there
are many buttons. It is that buttons, state switches, menus, modes, panes and
dangerous commands often look alike; scope is frequently hidden in a tooltip;
several features have multiple unrelated doors; and Junoview asks the user to
choose among 109 ribbon arrangements instead of making one strong default
interface predictable.

Four findings are concrete implementation defects rather than matters of
preference:

1. A right-click on one ordinary text object opens a 28-action, 11-section
   context menu inside a 215px, three-column grid. In the live app the labels
   wrapped almost character by character and the menu acquired both horizontal
   and vertical scrollbars.
2. Menus are not mutually exclusive. File and Present can remain open
   together; Background and Layouts can also remain open together. The latter
   visibly stacks one menu over the other. Present can remain
   aria-expanded=true after its menu has closed.
3. The editor emits two elements with id=qat-auto and two with
   id=deck-status. The live DOM confirmed both duplicate counts are two.
4. Inspector panes do not share one open/close controller. Tidy, print
   preflight and Standardise can all remain non-hidden at once even though the
   code comments say one pane should be open at a time.

The strongest overall recommendation is:

> Ship one stable Standard interface, one deliberately simplified interface,
> and at most one compact interface. Put every command in a searchable command
> palette. Use one right-hand inspector for Format, Animation, Accessibility
> and Data, and one Review centre for all checks. Do not make 109 rearrangements
> of the same 100-plus controls the user's information architecture.

The existing animation workflow illustrates the wider problem. Timeline lives
on Insert. With nothing selected it tells the user to select an item. Selecting
an item immediately switches the ribbon to Object, moving the user away from
the animation controls they just opened. The animation pane remains visible,
but the workflow has split across two contexts. The labels One by one, All at
once and Clear slide also describe neither their scope nor their destructive
effect clearly enough.

The underlying repository is healthy: all 937 collected tests passed, Ruff
passed, mypy passed for 37 source files, and the built-in self-test passed. The
findings therefore show what the current tests do not cover: whole-interaction
behaviour, discoverability, actual overflow and consistency between controls.

## The interaction grammar Junoview should adopt

Every control should belong to one of the following types. Its visual form,
label and ARIA state should follow from that type.

| Control type | Label rule | Behaviour | Example |
| --- | --- | --- | --- |
| Command | Verb plus object | Performs one action, then returns to rest | Add slide |
| Toggle | Stable noun plus visible switch/check | Turns one state on or off | Grid |
| Choice menu | Stable noun plus caret | Opens explicit choices; never cycles invisibly | Page size ▾ |
| Destination/pane | Noun naming the place | Opens one persistent surface and highlights while open | Animations |
| Mode | Segmented choices | Exactly one mode is selected | Document / Raw / Tree |
| Destructive command | Explicit verb plus explicit object | Warn colour, undo or confirmation as proportionate | Delete slide |
| Status | Sentence or compact readout, visually not a primary command | Clicking may open settings, but the status is readable without clicking | Saved to project · just now |
| Scope | Adjacent chip or menu | Says where the next command applies before it runs | This slide ▾ |

Additional rules:

1. A tooltip may explain a control; it must not supply the control's missing
   noun, scope or state.
2. Primary controls use words plus icons, matching the user-confirmed invariant
   in AGENTS.md:102-104.
3. The same action has the same name everywhere. Add slide and New slide should
   not be two names for the same operation.
4. A selection may reveal relevant controls, but it should not steal the
   user's current workflow. Selecting an object while working in Animations
   must not move them away from Animations.
5. Exactly one transient menu and one inspector pane may be active at a time.
6. Deck-wide actions must say Deck or All slides before they execute.
7. Red is reserved for destructive actions. A destructive label names what is
   removed.
8. Advanced features remain reachable through progressive disclosure and
   command search, not through dozens of alternative global arrangements.

## Detailed findings

### JVUX-01 — the object context menu is mechanically unusable

**Priority:** P0 interaction defect  
**Confidence:** reproduced live at 147c4ff; direct CSS and construction evidence

#### Live evidence

Right-clicking the only object on the test slide, an ordinary text box,
produced:

- 28 actionable buttons;
- 11 section headings;
- a narrow panel with three grid columns;
- labels wrapping into very thin columns;
- a horizontal scrollbar and a vertical scrollbar at the same time.

The menu included ordinary object actions, nine anchoring choices, component
creation, shrink-to-fit, object history, two visual-match modes, three lock
choices, private visibility, reading order, master choice, chart insertion,
guide-box insertion and paste state. This is not a shortcut menu any more; it
is an inspector forced into a small popup.

#### Implementation evidence

- src/junoview/assets/js/deck/25-selecting.js:1665-1685 creates
  div.sh-menu.canvas-menu and appends every row directly to it.
- The same function continues adding context-dependent sections through the
  rest of openCanvasMenu. A plain text object still reached 28 buttons in the
  live DOM.
- src/junoview/assets/css/deck.css:1461-1465 defines every sh-menu as a
  210px, three-column CSS grid.
- src/junoview/assets/css/deck.css:3216-3218 gives canvas-menu only a 215px
  minimum width and vertical overflow. It does not override display:grid,
  grid-template-columns or the fixed width from sh-menu.
- The new T115 Master row at
  src/junoview/assets/js/deck/25-selecting.js:2073-2081 adds another advanced
  feature to the same already-overloaded menu.

#### Required change

1. Make the immediate context menu a single-column list, approximately
   300-340px wide, with no horizontal overflow.
2. Keep only the high-frequency immediate actions:
   Duplicate, Cut, Copy, Delete, Bring to front, Send to back, Link and
   More properties.
3. Move anchoring, component, fit, matching, lock, visibility, reading order,
   master and data controls into the right-hand inspector.
4. Keep slide-level commands out of an object-level menu. Chart insertion,
   guide boxes, master selection and reading order belong to Insert, Design or
   the slide inspector.
5. Give the menu role=menu, rows role=menuitem or the appropriate checked
   variant, first-item focus, arrow-key movement and Escape-to-close.

#### Acceptance criteria

- Right-clicking any supported object at 1280 by 720 yields no horizontal
  scrollbar.
- Menu labels do not wrap below two readable lines.
- The default text-object menu has no more than 10 immediate rows.
- Advanced commands remain reachable in one click through More properties or
  directly in the inspector.
- A browser test checks scrollWidth <= clientWidth for the live menu.

### JVUX-02 — menus do not exclude one another and ARIA state becomes stale

**Priority:** P0 interaction and accessibility defect  
**Confidence:** reproduced twice, including after reload at 147c4ff

#### Live evidence

- File and Present were both visible simultaneously, covering the left and
  right sides of the editor.
- Background and Layouts were both visible simultaneously. Background sat on
  top of the larger layout gallery while both retained their own scroll areas.
- After clicking elsewhere, Present's menu disappeared but the control
  remained exposed as aria-expanded=true in the accessibility snapshot.

This creates hidden controls, accidental clicks and contradictory focus state.
It also explains why adding another individually wired menu repeatedly
reintroduces the same problem.

#### Implementation evidence

- File is locally managed at
  src/junoview/assets/js/deck/55-sections-and-strip.js:2247-2267.
  Its button handler calls stopPropagation and closes only dc-menu.
- Present is separately managed at
  src/junoview/assets/js/deck/55-sections-and-strip.js:1365-1384.
  It also calls stopPropagation and closes only play-menu.
- The Present document-click path at lines 1377-1380 sets menu.hidden=true but
  does not set aria-expanded=false.
- Individual ribbon menus use more local pairs of handlers. Layouts explicitly
  closes Page, but does not know Background exists. The live result was
  bg-menu and lay-menu both visible.

#### Required change

Create one OverlayController shared by all transient menus and popovers.
Opening a registered overlay must:

1. close the currently open overlay;
2. restore the previous trigger's aria-expanded=false;
3. set the new trigger's aria-expanded=true;
4. move focus into the new overlay where appropriate;
5. close on outside click, Escape, route/mode change and trigger removal;
6. return focus to the trigger on keyboard dismissal.

Dialogs and docked inspectors are separate overlay classes; a colour menu and a
File menu are not.

#### Acceptance criteria

- At most one visible transient menu exists after any sequence of trigger
  clicks.
- Every hidden menu's trigger has aria-expanded=false.
- File then Present, Background then Layouts, and Thumbnails then File are
  explicit browser test sequences.

### JVUX-03 — inspector panes also lack a single owner

**Priority:** P0 interaction defect  
**Confidence:** live DOM and code-path evidence

#### Live evidence

- After opening Tidy and then print Check, both #tidypane and #preflight
  returned isVisible()=true.
- Opening Standardise hid preflight but left both #stdpane and #tidypane
  visible.
- The panes share the same right-edge workspace. Depending on stacking and
  saved drag position, one can cover another or remain logically open while
  no longer visible to the user.

#### Implementation evidence

- src/junoview/assets/js/deck/05-figures-and-ribbon.js:1738-1761 says
  “one pane open at a time”, but syncPaneDock only scans for a visible pane and
  reserves width for the last one it sees. It does not enforce exclusivity.
- Print Check at src/junoview/assets/js/deck/00-page.js:1521-1531 simply
  toggles preflight and closes no sibling pane.
- Tidy at src/junoview/assets/js/deck/00-page.js:2066-2072 manually hides five
  named panes.
- Standardise at
  src/junoview/assets/js/deck/05-figures-and-ribbon.js:753-768 manually hides
  a different five-pane list and omits tidypane.
- Other panes repeat still other hard-coded lists. The lists have already
  diverged.

#### Required change

Create one InspectorController with openPane(id), closePane(id) and closeAll().
It should own:

- the single active pane id;
- each trigger's pressed/expanded state;
- dock/floating state;
- focus return;
- selection-sensitive refresh;
- closure during slide changes and mode changes.

No feature should manually enumerate sibling pane selectors.

This is also the correct foundation for the proposed unified Review centre and
the Format/Animation/Accessibility/Data inspector tabs described below.

#### Acceptance criteria

- At most one .selpane is visible after any sequence of pane commands.
- Trigger pressed state matches the active pane.
- Opening a second pane closes the first before measuring stage width.
- A single unit test covers the registry, and browser tests cover
  Tidy -> Check -> Standardise -> Animations.

### JVUX-04 — duplicated Save-status and Autosave nodes reveal an incomplete refactor

**Priority:** P1 correctness and maintainability defect  
**Confidence:** static source, live DOM and history evidence

#### Evidence

- src/junoview/assets/html/deck.html:180 emits deck-status.
- src/junoview/assets/html/deck.html:189 emits qat-auto inside a menu wrapper
  with auto-menu.
- Lines 219 and 222 emit a second deck-status and a second qat-auto.
- The live DOM reported:
  - #qat-auto count: 2
  - #deck-status count: 2
- src/junoview/assets/js/deck/00-page.js:70 defines $ as querySelector, so

- Git blame shows the improved save-status/autosave block was added in b4ae980
  on 2026-08-29 while the older 318cd19 block from 2026-08-20 remained below

Remove the obsolete second pair, keep one status and one autosave menu trigger,

The Save area should then be one coherent component:

- Save command;
- destination/status readout;
- autosave setting inside the readout's menu;
- one source of truth for dirty, saving, saved and failed states.

### JVUX-05 — 109 ribbon layouts replace a design decision with a catalogue

**Priority:** P1 systemic interaction and maintenance problem  
**Confidence:** live gallery plus counted source data

#### Evidence

- The live gallery title reported 109 layouts.
- src/junoview/assets/js/deck/07-ribbon-layouts.js:557 begins 108 explicit
  alternative layout objects. Default is prepended at lines 171-177, producing
  109 total.
- The file is 6,502 lines long.
- The whole split deck JavaScript directory is 37,537 lines, so alternative
  ribbon layouts alone are 17.3% of deck-editor JavaScript by line count.
- The catalogue includes mutually incompatible mental models such as Office
  ribbon, Deck/slide/object, Add/modify/show, One long group, Buttons/menus/
  switches, Ten things then More, Shortcut or mouse, and several product
  imitations.
- Each layout can declare its own tabs and its own selection destination.
  src/junoview/assets/js/deck/07-ribbon-layouts.js:35-47 documents that a
  selection may send the user to a different tab depending on the chosen
  layout.
- The Ribbon layouts button is a normal button physically inside the
  role=tablist at src/junoview/assets/html/deck.html:391-423. It therefore
  looks like another tab even though it opens a full-width chooser.

#### Why this harms use

- Tutorials, help text and screenshots no longer have one interface to teach.
- A collaborator cannot reliably say “open Design and choose X”.
- Selection behaviour, grouping and muscle memory differ by user.
- Every new control expands a large mapping/testing burden.
- The catalogue asks a new user to diagnose their own cognitive style before
  they understand the product.
- It hides the real work: choosing clear nouns, scopes and workflows for the
  default product.

#### Required change

Retain at most:

1. **Standard** — the one fully supported interface documented everywhere.
2. **Simple** — fewer visible commands, with More and command search providing
   full reach.
3. **Compact** — the same information architecture with reduced spacing, not
   a different taxonomy.

If per-user customisation remains, provide one editable custom layout built
from the Standard hierarchy. Do not ship 108 curated taxonomies.

Move Toolbar layout out of the tablist and into View or Preferences. Migrate
unknown stored layout ids to Standard with a one-time, reversible notice.

### JVUX-06 — animation is split across Insert, Object and a detached pane

**Priority:** P1 primary workflow defect  
**Confidence:** reproduced live; source explicitly implements the split

#### Live workflow

1. Open Insert.
2. Click Timeline.
3. The pane says “Select an item first, then pick an effect.”
4. Click the text object.
5. Selection automatically switches the ribbon from Insert to Object.
6. The animation pane remains at the right with None, Appear, Fade, Rise and
   Zoom, while the ribbon now shows Arrange, Text and Object controls.

The user has followed the product's instruction and been moved away from the
place they were using. The ribbon's animation preset actions have disappeared,
and there is no selected-object name in the pane to confirm what will animate.

#### Implementation evidence

- The animation group is on data-tab=insert at
  src/junoview/assets/html/deck.html:781-813.
- Timeline is a pane command, while effect controls are conditionally hidden.
- src/junoview/assets/js/deck/45-images.js:982-1068 builds the detached pane
  with How it appears, the effect choices, build order and Reading order.
- src/junoview/assets/js/deck/25-selecting.js:139-147 decides that a selection
  should switch to the active layout's selection tab.
- Line 475 performs that tab switch after formatting controls are revealed.
- Default declares selTab=object at
  src/junoview/assets/js/deck/07-ribbon-layouts.js:171-177.

#### Labels that make the workflow harder

| Current | Problem | Recommended |
| --- | --- | --- |
| Timeline | Sounds like a time scale, but opens all animation controls | Animations |
| One by one | Could mean selection/grouping; scope is hidden | Reveal items one at a time |
| All at once | Does not say which items or that one click is created | Reveal all items together |
| Clear slide | Sounds like deleting slide content | Remove all animations |
| How it appears | Does not distinguish entrance, emphasis or exit | Entrance effect |
| Build order — each row is one click | Encodes implementation rather than intent | Advance sequence |

#### Required interaction

- Selecting an object must not automatically leave an open Animation workflow.
- One stable inspector should contain tabs:
  - Format
  - Animation
  - Accessibility
  - Data/Source, when relevant
- Animations with no selection shows the whole-slide build sequence.
- Animations with a selection shows the selected object's name/type, effect,
  trigger, duration, delay and Preview.
- Each sequence row shows a thumbnail/name, order, On click / With previous /
  After previous, and timing. Dragging reorders it.
- Slide-level preset actions remain available inside the pane, clearly scoped.
- Remove all animations is separated from presets and supports Undo.

The feature-completeness gaps—exit/emphasis effects, duration, delay,
automatic starts, preview, motion paths, reduced motion and export loss—are
documented in reviews/2026-08-31_18-52.md. This finding is about making even
the present v1 understandable before expanding it.

### JVUX-07 — File is a 19-action catch-all and persistence has too many faces

**Priority:** P1 information architecture problem  
**Confidence:** live count and static markup

#### Evidence

The live #dc-menu contained 19 buttons. The flat menu at
src/junoview/assets/html/deck.html:76-147 mixes:

- New and Rename;
- refresh pictures and update figures;
- two auto-build modes;
- slide numbers and crop marks;
- History, Save target and Autosave;
- five export/download formats;
- Open;
- Discard changes;
- Delete presentation.

Separators provide no visible section names. At the same time the top bar has
Save, a destination chevron, a saved-status chip and a large cyan Autosave 2s
button. Rename is also available by clicking the centred presentation name.

The result is both overloaded and duplicated:

- file operations;
- source synchronisation;
- deck design;
- print setup;
- export/share;
- destructive presentation management;
- save settings.

#### Required change

Use the following ownership:

| Surface | Contents |
| --- | --- |
| File | New, Open, Save, Save a copy, Rename, History |
| Sources | Update linked figures and pictures, automatic refresh/build |
| Export / Share | Review package, PDF/Print, PowerPoint, standalone HTML, Junoview copy |
| Design / Page setup | Slide numbers, crop marks, page background, master |
| Presentation settings | Autosave, default save destination, talk defaults |
| Manage presentation | Discard changes and Delete presentation, separated and confirmed |

The top bar should show one save component:

**Saved to project · just now ▾**

Its menu can contain save destination and autosave interval. Autosave is a
status/setting, not a second primary action competing visually with Save.

The Present split button is a sound pattern, but its menu should keep named
sections and ensure every toggle visibly exposes state. File and Present must
share the central OverlayController from JVUX-02.

### JVUX-08 — notebook filters are invisible three-state cyclers

**Priority:** P1 discoverability and state-control problem  
**Confidence:** markup, handler and live labels

#### Evidence

- The live toolbar showed Plots On, Markdown On, Code Fold and Output On.
- src/junoview/assets/js/app.js:536-539 explicitly says all four buttons cycle
  Visible -> Collapsed -> Hidden and that their labels show current state, not

- src/junoview/assets/js/app.js:600-604 maps those states to the shortened
  words On, Fold, Off and Mix.
- src/junoview/assets/js/app.js:1618-1635 advances the state on each click.
- The Output tooltip in
  src/junoview/assets/html/page.html:55-58 says “Click to show / hide”, even

  disagree.
- Plot types, Code cell types and Output types are separate icon-only buttons

- Those icon-only advanced doors conflict with the explicit words-plus-icons
  invariant in AGENTS.md:102-104.
- A user who wants Hidden from On must know how many clicks to make, may

#### Required change

Replace each cycler with one labelled menu:

- **Plots ▾**
  - Show
  - Collapse
  - Hide
  - Types…
- **Code ▾**
  - Show
  - Collapse
  - Hide
  - Cell types…

The current state should appear as a checkmark and optionally a compact state
chip beside the stable noun. It should never require repeated clicking to
discover the state set.

Keep Apply to: All sections as an adjacent scope control, visually distinct
from the filters. Reset filters should state its scope in the confirmation
toast.

Raw, Tree and the formatted document are modes, not independent toggles. Make
them one segmented choice: **Document | Raw | Tree**. Present remains a
command operating on the selected mode.

### JVUX-09 — five review/check concepts are separate and inconsistently named

**Priority:** P1 information architecture problem  
**Confidence:** live workflows and distinct implementations

Junoview currently has at least:

- Check, whose pane is actually titled Before you print;
- Tidy page, which finds alignment, gaps and duplicates;
- Standardise, which checks text and figures across the deck;
- Check for drift inside the deck-wide Design surface;
- Export for review, which writes content/provenance rather than opening a
  checking workflow.

The same user question—“is this ready?”—has been split by implementation
history. The labels do not reveal the distinctions:

- Check is too generic for print preflight.
- Standardise sounds like it will modify the deck, but it opens a report.
- Check for drift is project jargon.
- Tidy page sounds like an automatic command, but first opens a report.
- “nothing out of true” in the Tidy empty state is distinctive prose, but not
  immediately understandable status language.

The fragmented pane-opening code in JVUX-03 lets these surfaces compete
mechanically as well as conceptually.

#### Required change: one Review centre

Provide one worded **Review** command with categories:

1. Content and reading order
2. Accessibility and contrast
3. Layout and spacing
4. Style consistency
5. Source freshness
6. Print and export readiness

Each finding should include:

- severity;
- slide/object;
- evidence;
- Fix, Ignore once and Suppress rule where appropriate;
- scope: Current slide / Section / Whole deck;
- navigation to the affected object.

Map existing engines into this centre rather than rewriting them:

- preflight() -> Print and export;
- tidyFindings() -> Layout and spacing;
- standardise() -> Style consistency;
- reviewLints() and reading order -> Content/accessibility;
- source staleness -> Source freshness.

Rename Export for review to **Export review package…** and keep it in Export /
Share. It exports evidence; it is not the Review centre itself.

### JVUX-12 — the contextual Object tab is useful, but automatic tab stealing and vague labels undermine it

**Priority:** P2 workflow consistency  
**Confidence:** live selection behaviour and source

The contextual Object tab is a reasonable idea. The problem is that selecting
an object automatically activates it, even when the user is in Insert,
Animations, Design or Review. That makes ordinary selection a navigation
command.

The live text-object tab showed:

- Duplicate, Front and Back;
- A−, A+, an unclear size readout, font, B/I/U/S and list buttons;
- Keep shape;
- Size & position.

Recommended changes:

- Reveal Object/Format when selected, but do not activate it automatically if
  a persistent pane or explicit workflow is open.
- Rename the tab **Format**; the selected object's type and name should appear
  in the inspector header.
- Use full action labels **Bring to front** and **Send to back**. Their current
  tooltips at src/junoview/assets/html/deck.html:1101-1106 carry the missing
  verbs.
- Rename Keep shape to **Lock aspect ratio**. Lines 1463-1468 reveal that this
  is its actual meaning.
- Keep Size & position, but open it as the Size/Position section of the same
  inspector instead of another detached pane.
- Keep text size as a labelled value: **Text size 24 pt**, with minus and plus
  as secondary controls.

### JVUX-13 — workspace controls and tiny action icons do not follow the product's own visual rule

**Priority:** P2 consistency and learnability  
**Confidence:** source and live toolbar

Examples:

- App theme, support and help are icon-only at
  src/junoview/assets/html/page.html:167-180.
- Presentations-panel Collapse and Auto-hide are icon-only at lines 325-333
  and use the same base icon.

- The editor's Ko-fi support link is icon-only at
  src/junoview/assets/html/deck.html:249-251.

  **Support** with its heart icon.
- Presentations-panel controls become **Collapse panel** and **Auto-hide**

## Proposed target interface

The target keeps Junoview powerful without keeping everything visible at once.

### Top utility bar

| Left | Centre | Right |
| --- | --- | --- |
| File; Saved to project ▾; Undo; Redo; Search | Presentation name | Theme; Help; Review; Present ▾ |

Search should cover both content and commands. A command result shows:

- icon and stable label;
- where it normally lives;
- current state;
- scope;
- shortcut;
- disabled reason when unavailable.

This gives every advanced feature a reliable second door and removes the need
for 109 ribbons.

### Stable ribbon

**Home**

- Slides: Add slide, Duplicate slide, Delete slide, Layout
- Arrange: Match layout, Align/Distribute when selected
- Workspace: Layers, Notes, Rulers/Grid/Guides through View

**Insert**

- Text, Notebook content, Image, Table, Chart, Shape, More
- Animations opens the Animation inspector; it is not a bundle of ambiguous
  whole-slide preset buttons ahead of Insert

**Design**

- Theme, Page size, Background
- Master
- Layouts
- Style system

**Contextual Format**

- Appears when an object is selected
- Does not automatically steal focus from another active workflow
- Opens the right inspector's appropriate section

View preferences should live in one **View ▾** menu, not among slide-edit
commands: Slide thumbnails, Rulers, Grid, Guides, Full-screen editor and Move
toolbar to side.

### Right inspector

One inspector shell, one open pane, stable tabs:

1. Format
2. Animation
3. Accessibility
4. Data/Source, only when relevant

The header always names the selection, for example:

**Text box · “Blocking frequency”**

With no selection it switches to slide-level properties rather than becoming
an empty pane.

### Review centre

Review is one persistent surface with category filters and slide/deck scope.
It reuses the existing checking engines. Opening Review never allows Tidy,
Standardise and Preflight to stack as separate panes.

### Filmstrip

- One term: Add slide, used both in ribbon and strip.
- Thumbnail / Headings / Both is a view selector.
- Overview is a separate destination, not a row inside a menu named
  Thumbnails.
- Reorder is primarily drag-and-drop; keyboard users get Move up/down in
  Slide actions.
- Delete always says Delete slide and supports Undo.

## Tests that should be added

The 937 passing tests prove current intended behaviour but do not catch the
defects above. Add:

1. **Unique IDs:** parse assembled page/deck HTML and fail on any duplicate id.
2. **Overlay exclusivity:** click every registered menu pair; assert no more
   than one transient overlay visible and all ARIA state correct.
3. **Pane exclusivity:** open every pair of inspectors; assert one visible.
4. **Context-menu geometry:** in a real browser, assert no horizontal overflow
   and readable minimum row width.
5. **Animation continuity:** open Animations, then select an object; assert the
   Animation workflow remains active and the selection is named.
6. **Command discoverability:** every public editor capability has either a
   visible primary door or a command-search entry with a non-empty label and
   location.
7. **Scope contract:** deck-wide commands expose Deck/All slides in visible
   text before invocation.
8. **Label contract:** one action id maps to one stable user-facing label.
9. **Responsive screenshots:** Standard interface at 1280x720 and 1440x900,
   light/dark, with menus and inspector open.
10. **Keyboard path:** tab/arrow/Enter/Escape through File, Insert More,
    animations and Review.

Do not replace all existing substring tests. Keep tests that pin important
decisions, but add behavioural browser tests for interactions that only exist
when several individually correct components meet.

## Definition of done for the redesign

The redesign is complete when:

- one documented Standard interface is the same for every new user;
- no more than three layout density modes ship;
- every feature can be found by stable location or command search;
- no menu can overlap another transient menu;
- no inspector pane can compete with another;
- no duplicate HTML id exists;
- context menus are short, readable and free of horizontal scrolling;
- selecting an object does not unexpectedly abandon the user's workflow;
- animation has one coherent, selection-aware surface;
- Review unifies layout, style, accessibility, source and print checks;
- File contains file operations rather than every setting in the product;
- deck-wide scope is visible before an action runs;
- labels say what will happen without requiring a tooltip;
- words-plus-icons is true in the rendered interface, not only ARIA metadata;
- responsive and keyboard browser tests cover the assembled product.

## Bottom line

Junoview does not need fewer capabilities. It needs fewer competing ways to
reach them.

The product already contains many of the hard engines: source-aware figures,
native charts, masters, animation builds, style checks, layout checks,
preflight, provenance, review export and multiple output formats. The next
high-leverage step is to stop adding another local button, menu or ribbon
arrangement for each engine and give all of them the same interaction grammar.

Repair the shared menu/pane substrate first. Then ship one strong default,
searchable commands, one inspector and one Review centre. That will make the
existing power feel intentional instead of hidden, and it will give future
PowerPoint-, Excel- and Junoview-specific features an obvious place to go.
