## Executive summary

Junoview's source checkout is unusually well tested and the current UI is
substantially more coherent than the historical backlog suggests. All 774
tests pass, Ruff and mypy pass, the built-in smoke test passes, the current
generated demo opens without console errors, and the ribbon remains usable at
the three desktop widths sampled.

There is nevertheless one release-blocking defect: the wheel omits every
JavaScript fragment that makes up the deck editor. A clean `pip` installation
therefore cannot assemble `assets.deck_js()` and cannot render the normal app
page. The source checkout and generated `docs/` build hide this because the
files exist beside the Python package during development.

The next most important findings are that the recently added Markdown/LaTeX
image-source path is incomplete in the app, the full-screen deck does not
isolate the underlying document for assistive technology, and the backlog can
no longer be trusted to identify unfinished agent work. The repository also
contains 3.8 GB of untracked browser profiles that the supplied cleaner does
not see.

No uncommitted or partially staged product code was found. Both registered
Claude worktrees are clean. One is a stale divergent branch containing older
versions of work later implemented and reconciled on `main`; it does not
currently contain an uncommitted feature to rescue.

## Confirmed findings

### P0 — Published wheels omit the entire deck editor

> **Done (2026-09-01)** — T95 `274deab`, T96 `a5b5e29`. Package data now
> names `assets/js/deck/*.js`, and the self-shadowing installed-package test
> was replaced by one that globs every declared package-data pattern against
> `src/junoview` and fails on the next unshipped subdirectory, not just this
> one.

Evidence:

- `pyproject.toml:63-69` declares `assets/js/*.js`, but not
  `assets/js/deck/*.js`.
- `assets.deck_js()` in `src/junoview/assets/__init__.py` reads fifteen named
  files below `assets/js/deck/`.
- A clean wheel built from `HEAD` contained zero paths below
  `junoview/assets/js/deck/`.
- Importing that wheel and calling `assets.deck_js()` raised
  `FileNotFoundError` for `junoview/assets/js/deck/00-page.js`.
- `.github/workflows/ci.yml:58-67` says its clean-wheel render is intended to
  catch exactly this class of problem, so the build job on this revision
  should be considered suspect until its remote result is checked.

Impact:

- `pip install junoview` can import the package but fails when the renderer
  assembles the page assets. The CLI app and ordinary HTML export are broken
  for installed users.
- The live site still works because `docs/` was generated from the source
  checkout, not because the wheel is healthy.

Recommended fix:

1. Add `assets/js/deck/*.js` to package data.
2. Add a fast local test that builds/opens the wheel and asserts that every
   `DECK_PARTS` member exists. Do not rely only on the remote build job.
3. Install that wheel into a clean environment and drive both a notebook
   render and `--build-web` before publishing another release.

### P1 — Markdown and LaTeX figures are not a complete app feature

> **Partly done (2026-09-01)** — T100 `a9b9b7c` opened every parseable
> source in the app, T101 `ebfa845` threaded a base directory through the
> producers so a sibling raster/SVG figure embeds as a data URI, a PDF/EPS
> becomes a named card and an empty src draws nothing, and T122
> `6cd2cca`/T123 `c8c32a7` made source figures first-class and refreshable
> from disk (T102/T103 deepened both producers). Addressed differently to
> the ask: figures are embedded at parse time rather than served over a
> route, which T101 records as the safer seam. Still open: the web build's
> multi-file/folder import — a file dropped on the Pyodide build hands over
> only its own text, so a figure beside it cannot resolve (`web_parse`
> passes no base, said explicitly in T101's note).

Evidence:

- `src/junoview/notebook/sources.py:108-124` keeps an image path exactly as
  written and emits it directly as `<img src="...">`; its own comment admits
  that the path is wrong whenever output is not saved beside the source.
- `load_doc()` knows the source `Path` but does not pass its parent to the
  producer (`loader.py:29-40`).
- The local server serves only `/` and `/api/list` on GET
  (`server/routes.py:63-93`), so `fig/trend.png` in an opened Markdown or TeX
  file resolves to an unserved HTTP path and returns 404.
- A file dropped onto the Pyodide web build supplies only its text; related
  image files are neither uploaded nor bundled.
- The LaTeX test fixture explicitly turns `fig/trend.pdf` into an `<img>`
  (`tests/test_sources.py:56,145`). Browsers do not render a PDF as an image,
  so the test proves string preservation rather than a visible figure.

Impact:

- T91 is marked complete, but the most important Overleaf/Markdown case—a
  document with local figures—does not display those figures in the app.
- The behaviour changes depending on how the same source is opened: a CLI
  export saved beside a PNG may work; the app, web drop, a relocated output,
  and ordinary Overleaf PDF graphics do not.

Recommended fix:

- Carry a source origin/base path through `Document` production.
- In app mode, serve explicitly authorised source assets through a tokened,
  traversal-safe route, or embed them as data URIs during parsing.
- Give the web build a multi-file/folder import path so related assets travel
  with the document.
- Treat PDF/SVG/raster sources deliberately instead of sending all of them
  through an `<img>` string and testing only the string.

### P1 — The deck overlay leaves the underlying application active

> **Done (2026-09-01)** — T104, `ec5258f`. The fix is JS and mode-aware, as
> the group-13 audit corrected: the full-screen deck sets `inert`/`aria-
> hidden` on the document surfaces behind it and restores them on close,
> while create mode's side panel stays a live drag source by design;
> `tests/test_present_mode.py::test_the_document_behind_the_deck_goes_inert`
> pins it, and the same pass revived the overview panel's dead Escape
> branch.

Browser evidence while the deck editor was visibly full-screen:

- `#deck` was `position: fixed`, visible, and not inert.
- The underlying `<main class="stage">` remained `display:block`,
  `visibility:visible`, non-inert, and approximately 12,670 px tall.
- The browser's semantic DOM snapshot exposed the underlying notebook
  navigation and document while the deck was open.
- `body.deck-open` only sets `overflow:hidden`
  (`assets/css/deck.css:22`). Toggling the class at
  `55-sections-and-strip.js:1046-1047` does not apply `inert` or
  `aria-hidden` to the background, establish a dialog boundary, or restore
  focus when the editor closes.

Impact:

- A screen-reader user can encounter two applications at once: the visible
  editor and the notebook underneath it.
- Keyboard focus can escape into controls hidden behind the fixed editor.
  This is an accessibility defect and can feel like shortcuts or Tab have
  stopped working.

Recommended fix:

- When the deck opens, make the background shell inert and semantically
  hidden; restore it on close.
- Move focus into a sensible editor control, contain Tab within the active
  surface, and return focus to the presentation row that opened it.
- Add an end-to-end keyboard/accessibility regression test; DOM substring
  checks will not catch this.

## Product completeness against the stated ambition

### Excel parity is not present

> **Done (2026-09-01)** — T113, `41b6865`, addressed differently to full
> parity: the user decided Excel IS in scope, values only, so `.xlsx` is
> read by a stdlib zipfile+XML `parse_workbook` behind the new
> `doc_from_bytes` seam, each sheet a table card that can become a
> refreshable chart. Formulas, number formats, styles, merges and workbook
> export are deliberately not read, and the entry records each cut — so the
> code no longer calls a CSV preview "the Excel half".

The code calls CSV/TSV “the Excel half” (`sources.py:21-30`), but it is a
read-only HTML preview of one delimited table:

- No `.xlsx`/`.xls` workbook import.
- No sheets, formulas, cell types, styles, merged cells, charts, tables,
  filtering/sorting UI, pivots, Power Query, named ranges, data validation,
  what-if tools, or workbook export.
- The first row is always treated as a header.
- Rendering is capped at the first 500 data rows.

This is reasonable for a stdlib-only notebook viewer, but it is not a partial
Excel implementation that can be described as nearly complete. If the goal is
genuinely “PowerPoint and Excel and more”, workbook support needs its own
architecture and backlog rather than a checked source-import task.

### PowerPoint parity is broad but deliberately incomplete

> **Partly done (2026-09-01)** — export fidelity closed most of the named
> losses: crops and transitions (T107 `9ae9b80`), speaker notes (T108
> `a05f596`), tables plus a pre-export loss report and honest help prose
> (T109 `059caaf`), builds and links verified in PowerPoint itself (T110
> `b3f874e`), baked masters (T115 `f62ea2e`) and real data-bound charts
> (T117 `39984f3`), while T125 `8f1bf96` wrote the notebook-first boundary
> down as this section asked. Deferred by decision: full `.pptx` import
> (T114, the user's "come back for this for the full import at a later
> date"). Equations still need a second LaTeX front end and hosted/live-
> audience features stay cut (T119 parked) — both recorded, not built.

Junoview has a strong slide/poster editor, native `.pptx` export, animation
builds, layouts, design tokens/types, history, presenter tools, figures, and
standalone/PDF export. The repository also explicitly records boundaries that
conflict with full PowerPoint parity:

- PowerPoint export cannot faithfully carry table frames, crops, or typeset
  equations (`CHANGELOG.md:1799-1808`).
- No `.pptx` import path was found.
- Real-time collaboration/review, text flow between boxes, advanced vector
  editing, full infinite canvas, live audience features, and generative media
  are explicitly cut in `TASKS.md:1572-1586`.

These may be good scope choices. They should, however, be presented as product
boundaries rather than as a completed Office-equivalent feature set. The
current architecture is best understood as a notebook-first scientific
presentation system, not a general Office replacement.
