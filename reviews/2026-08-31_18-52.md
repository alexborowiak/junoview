## Executive verdict

No: the implemented features are not all complete in the ordinary meaning of
their names, and animations are one of the clearest examples.

The repository is healthy at the engineering-gate level: **924 tests pass**,
Ruff passes, mypy reports no errors in 37 source files, the built-in self-test
passes, the committed checkout is clean, and a live browser pass produced no
console errors. That proves the behaviour the tests describe is stable. It does
not prove that the feature surface is complete.

The most important completeness findings are:

1. Animations are a small on-click entrance/build system, not yet a complete
   animation system. There is no preview, duration, delay, direction, easing,
   After Previous, exit/emphasis effect, motion path, object trigger or
   automatic slide timing.
2. Some existing animation choices do not play as labelled: a rotated Rise or
   Zoom silently becomes Fade; the transition described as a cross-fade is
   only a fade-in of the new slide; separately-created slides can Magic-Move
   unrelated objects through a heuristic match.
3. Reduced-motion handling is incomplete. Slide transitions respect the OS
   preference, but entrance animations still run because the reduced-motion
   CSS disables transitions, not the `animation` property used by Fade/Rise/
   Zoom.
4. PowerPoint export changes Rise/Zoom builds to Fade and changes Move Matching
   Objects to a left Push. The first loss is listed before export; the second is
   not included in the export-loss dialog even though help text explains it.
5. The deck format does not document the `anim` field, and the validator does
   not validate common annotation fields at all. A deliberately malformed
   animation plus a totally unknown field validates with no problems.
6. Authored reading order now controls Junoview's build order, figure numbers,
   matching and review text, but it deliberately does not control HTML DOM
   order or PowerPoint shape order. It is therefore not yet a complete
   screen-reader/export reading-order feature.
7. Native charts are a useful v1, but they lack chart accessibility, axis
   semantics, data-error handling, in-editor series styling, stacking,
   secondary axes, an embedded PowerPoint workbook and live linkage for charts
   created from a deck table.
8. T110 is checked even though its title contains four capabilities and its
   own completion note says only two shipped. Equations still flatten to text
   in PowerPoint and true masters are still unbuilt.
9. The review system exports only `reviewLints()`, not all the checking surfaces
   the task said should be consolidated. It also has fixed thresholds and no
   per-finding suppression.
10. Several correctness and UI findings from the previous review still exist:
    source refresh can falsely report success after an I/O failure; a deck with
    no notebook references hides its way back to notebooks; Overview excludes
    arrows despite saying “Every object”; range clamping can store 1–999 for a
    ten-slide deck; and Layout Ideas still does not preview built-in templates.

The right response is not to declare the existing work bad. Much of it is good,
and several limits are documented honestly in `TASKS.md`. The follow-up is to
split those limits into explicit tasks, stop using a checked box as evidence of
full Office-class completeness, and fix the cases where the UI promises one
effect but the runtime does another.

## Detailed findings

### JVC-01 — animations are an intentionally small v1 presented as a complete surface

> **Partly done (2026-09-01)** — the honest-labelling ask landed with T140,
> `514e857`: Timeline is now Animations, Clear slide is Remove animations,
> and the pane heading reads Entrance effect. Still open: preview, Appear on
> the ribbon, effect glyphs, timing/start/easing fields,
> exit/emphasis/motion-path milestones, title/subtitle builds and
> behavioural tests.

**Priority:** P1 product completeness  
**Type:** checked feature is much narrower than users expect  
**Confidence:** high; exhaustive UI/model evidence plus live inspection

#### What actually exists

- Per-object entrance effects: None, Appear, Fade, Rise and Zoom at
  `src/junoview/assets/js/deck/45-images.js:993-1000`.
- A build is an integer `anim.order`; equal values appear on the same click.
  The model is enumerated at `15-annotations.js:998-1029`.
- Build editing provides Move Earlier/Later, “Appear with previous” and “Own
  click” at `45-images.js:1002-1058`.
- Whole-slide shortcuts provide One by one, All at once and Clear slide at
  `45-images.js:1123-1155`.
- Slide transitions are only Cut, Fade and Move Matching Objects at
  `45-images.js:1693-1701` and `DECK-FORMAT.md:88`.
- All Move transitions use a fixed `TRANS_MS = 420`; entrance durations are
  fixed in CSS: Fade 0.45s, Rise 0.5s and Zoom 0.45s at
  `src/junoview/assets/css/deck.css:1717-1726`.

#### What is missing

- no preview/replay button in the pane or ribbon;
- no duration, delay, easing or effect direction;
- no **After Previous** or timed automatic build;
- no entrance trigger tied to clicking another object;
- no exit effects;
- no emphasis effects;
- no motion paths;
- no animation painter/copy-animation command;
- no sound/media timing;
- no per-slide automatic advance or recorded slide timings driving playback;
- no animation of title-layout `title`/`subtitle` objects: build enumeration
  only walks `s.annots` (`15-annotations.js:998-1029`) and render-time build
  handling explicitly skips indices `t` and `s`
  (`20-notes-and-tables.js:2351-2357`);
- no effect thumbnails or icons in the Timeline chooser: it creates plain-text
  buttons with `b.textContent = p[1]` (`45-images.js:993-1000`). This is
  inconsistent with Junoview's words-plus-icons ribbon style and makes effects
  impossible to judge without entering Present mode;
- the instant **Appear** effect exists inside Timeline but is absent from the
  selected-item ribbon buttons. The pane lists it at `45-images.js:993`; the
  ribbon HTML and event wiring list only None/Fade/Rise/Zoom at
  `assets/html/deck.html:785-794` and `45-images.js:1109-1112`.

#### What should be added/changed

1. Document the current model as “on-click entrance builds” until it grows.
2. Add a **Preview** control that replays the selected effect, selected build or
   whole slide without entering Present mode.
3. Make Appear available beside the other effect buttons.
4. Use words plus a small animated/static glyph for every effect, never
   icon-only.
5. Extend `anim` deliberately, for example with `start` (`click`, `with`,
   `after`), `duration`, `delay`, `easing`, `direction` and optional
   `triggerOid`. Normalise and validate every field before adding UI.
6. Treat exit/emphasis/motion-path support as a second explicit milestone. Do
   not hide those omissions under the generic word “Animations”.
7. Either let title/subtitle participate in the same build model or show a
   clear reason they cannot be animated.
8. Add behavioural browser tests for timing, preview, title objects, same-step
   builds, After Previous and reduced motion. Current tests mostly pin strings
   and the existence of functions.

### JVC-02 — reduced motion disables transitions but not entrance animations

> **Not yet addressed (2026-09-01)** — core.css still clears only
> transitions under reduced motion and deck.css guards only `.slide`; the
> `.an-anim-fade/rise/zoom` entrance classes remain unguarded, so builds
> still animate when the OS asks for reduced motion.

**Priority:** P1 accessibility/correctness  
**Type:** user preference is only partly honoured  
**Confidence:** high; CSS/runtime contradiction

Evidence:

- `motionOK()` checks the OS preference at
  `src/junoview/assets/js/deck/45-images.js:1746-1750`.
- `playFlip()` refuses to play slide Fade/Move when motion is reduced at
  `45-images.js:1795-1802`.
- The transition menu labels effects “not on this machine” through calls in
  `55-sections-and-strip.js:445` and `:484`.
- Entrance effects are CSS **animations**, not transitions:
  `.an-anim-fade`, `.an-anim-rise`, `.an-anim-zoom` at
  `assets/css/deck.css:1717-1726`.
- The global reduced-motion rule at `assets/css/core.css:1153-1156` sets only
  `transition:none` and `scroll-behavior:auto`; it does not set
  `animation:none`.
- The only animation-specific reduced-motion rule is
  `.slide{animation:none}` at `assets/css/deck.css:3298`. Entrance classes are
  on individual annotation elements, not the `.slide`.
- `tests/test_slide_sections.py:822-834` calls the feature complete after
  checking only `motionOK()` and `playFlip()`. It never proves an
  `.an-anim-*` entrance is disabled.
- The live test machine reported `prefers-reduced-motion: reduce`, making this
  a real user configuration, not a theoretical branch.

Effect: the menu implies animations are disabled on this machine while
Fade/Rise/Zoom builds can still animate when revealed.

Required change:

- Under reduced motion, disable `.an-anim-fade`, `.an-anim-rise` and
  `.an-anim-zoom` animation duration/name, while still revealing the item
  immediately.
- Use one shared `motionOK()`/CSS contract for slide transitions and builds.
- Add a browser/computed-style test under forced reduced motion. The test must
  inspect the entrance class, not only search the assembled JavaScript.
- Consider a presenter-level override only if it does not override an OS
  accessibility preference silently.

### JVC-03 — selected animation effects can be silently substituted

> **Not yet addressed (2026-09-01)** — the substitution branch still ships
> verbatim (`if(ba.rot&&(atype==='rise'||atype==='zoom')) atype='fade';`,
> now 20-notes-and-tables.js:2368), with no nested-wrapper fix, disabled
> state or warning.

**Priority:** P1 UX correctness  
**Type:** runtime does not match model/UI  
**Confidence:** high; explicit branch

For a rotated item, Rise and Zoom do not play. The render path changes either
to Fade:

- `src/junoview/assets/js/deck/20-notes-and-tables.js:2375-2379` says the
  transform animation would fight rotation and snap, then executes
  `if(ba.rot&&(atype==='rise'||atype==='zoom')) atype='fade';`.

The saved model still says Rise or Zoom, the ribbon still reports Rise or Zoom,
and the Timeline chip still names the saved type. There is no warning, disabled
state or badge. This is a direct explanation for animations feeling “weird”.

Required change:

- Best fix: animate a nested wrapper so the entrance transform and the
  object's rotation use separate transform layers.
- Acceptable short-term fix: disable Rise/Zoom for rotated objects and explain
  why before the user selects them.
- Never keep one label in the model/UI and run a different effect.
- Add tests for 30° rotated Fade/Rise/Zoom objects and verify both mid-flight
  and final transforms.

### JVC-04 — Fade is not a cross-fade, and Move can pair unrelated objects

> **Not yet addressed (2026-09-01)** — the transition menu still calls Fade
> "A short cross-fade" (45-images.js:1717) while `playFlip` fades in only
> the new slide, and `matchKey` still pairs objects by style/part/kind alone
> with no explicit continuity tool or heuristic-match warning.

**Priority:** P2 animation quality  
**Type:** effect naming and matching quality  
**Confidence:** high from control flow

#### Fade naming mismatch

`45-images.js:1695` describes Fade as “A short cross-fade”. In reality,
`captureFlip()` measures the outgoing slide, normal slide rendering removes
that slide, and `playFlip()` applies opacity 0→1 only to the newly rendered
`.slide` (`45-images.js:1753-1772` and `:1806-1817`). The old and new slides
are never simultaneously blended. This is a fade-in over the stage/background,
which can flash and feel harsher than a cross-fade.

Required change: either preserve an outgoing snapshot/overlay until the blend
finishes, or rename the choice to **Fade in** and tune the background so the
result is intentional.

#### Magic-Move matching ambiguity

`flipKeys()` prefers the same `oid`, which is reliable after duplicating a
slide. If there is no shared `oid`, it falls back to `matchKey(a)` plus the
item's position in reading order (`45-images.js:1717-1735`). `matchKey()` is
coarse: text matches by text style, cells by part, and everything else only by
kind (`35-arranging.js:319-329`). Two separately-created slides can therefore
pair the first body text with an unrelated first body text, or the first image
with a different first image.

Required change:

- expose an explicit “Match across transition” continuity ID/tool;
- display which objects Move believes are paired before playback;
- restrict heuristic fallback to high-confidence pairs (same durable source,
  same name, same component member, or explicit user match);
- let unmatched entering/leaving objects use an explicit entrance/exit policy;
- add a warning when a Move transition relies on kind/order heuristics.

### JVC-05 — PowerPoint changes animation semantics, and one loss is not in the loss dialog

> **Not yet addressed (2026-09-01)** — `pptxLosses()` still counts only
> skipped cells, equations, crop outlines and rise/zoom builds; there is no
> check for `trans==='move'`, so the Move→Push substitution remains
> undisclosed in the actual export confirmation.

**Priority:** P1 export fidelity  
**Type:** documented approximation plus incomplete disclosure  
**Confidence:** high

Evidence:

- PowerPoint timing supports Appear and Fade exactly; every Rise/Zoom build is
  emitted as a Fade at `src/junoview/assets/js/pptx.js:715-740`.
- All emitted fade timing is fixed at 500 ms (`pptx.js:738`), independent of
  Junoview's fixed 420/450/500 ms runtime values.
- `pptxLosses()` does count Rise/Zoom substitutions before export at
  `assets/js/deck/60-saving-and-export.js:1647-1657`.
- Junoview's Move Matching Objects transition is not exported as object
  continuity. `pptx.js:421-434` maps it to `<p:push dir="l"/>`.
- `help.html:584-592` says Move becomes Push and says everything lost is named
  when exporting.
- `pptxLosses()` contains no check for `trans === 'move'`; its only animation
  warning is Rise/Zoom. Therefore a user who does not remember the help page is
  not told in the actual export confirmation that an object morph becomes a
  whole-slide push.

Required change:

1. Count every Move transition in `pptxLosses()` and name the Push
   substitution in the pre-export dialog.
2. Put an export-fidelity badge directly beside effects that are approximate.
3. If reliable OOXML Morph generation is not possible, consider exporting
   Move as a simpler Fade rather than a directionally unrelated Push, or let the
   user choose the fallback.
4. When animation timing fields are added, export supported timings and report
   unsupported ones individually.
5. Add a byte-level and dialog-level test proving every approximation is both
   emitted and disclosed.

### JVC-06 — `anim` is absent from the documented schema, and annotation validation is mostly inert

> **Not yet addressed (2026-09-01)** — `anim` is still absent from both
> DECK-FORMAT.md and `deck_schema.py` (the only schema additions since the
> review are T115's `masters`/`mast`), and `_check_annot()` still never
> validates the common annotation keys.

**Priority:** P1 data integrity / automation  
**Type:** checked schema/validator feature is incomplete  
**Confidence:** high; direct probe

T33 is checked as “Deck JSON schema doc + validator”, but the item validator
does not validate the declared common item table and does not know the
animation model.

Evidence:

- `DECK-FORMAT.md:125-142` lists every common item field but contains no
  `anim` row.
- `src/junoview/notebook/deck_schema.py:145-206` defines `ANNOT_COMMON` but
  also contains no `anim` entry.
- `_check_annot()` at `deck_schema.py:269-307` checks kind, required geometry,
  cell `ref` and a narrow token condition. It never calls `_check_keys()` with
  `ANNOT_COMMON` and has no per-kind optional-field table.
- `_check_keys()` does know how to warn about unknown keys
  (`deck_schema.py:241-258`), but it is used for decks/slides, not annotations.
- Direct probe run during this review:

  ```python
  validate_deck({
      "name": "d",
      "slides": [{"layout": "blank", "panes": [], "annots": [{
          "k": "text", "x": 1, "y": 1, "text": "x",
          "anim": {"type": "warp", "order": "bad"},
          "totallyUnknown": 42,
      }]}],
  })
  ```

  returned `[]`.

This means strict save/automation can accept an invalid animation type, wrong
order type, unknown annotation field and many malformed optional properties
without warning.

Required change:

- document `anim` and its allowed types/fields in `DECK-FORMAT.md`;
- add it to the Python schema and normalisation contract;
- make `_check_annot()` validate common keys plus kind-specific optional keys;
- validate enums (`ct`, transition/effect types, anchors, shapes), nested
  structures (`series`, `anim`, `link`, `crop`) and value types;
- keep forward compatibility by warning on unknown fields rather than rejecting
  them, as the format already promises;
- add behavioural validator tests with malformed common fields and unknown
  keys. Do not settle for parity/string-presence tests.

### JVC-07 — authored reading order is not yet semantic reading order

> **Not yet addressed (2026-09-01)** — `renderAnnots` and the PowerPoint
> exporter still walk `s.annots` in storage order; `orderedIdx` still feeds
> only figure numbers, builds, matching and review, so DOM order and
> exported shape order remain stacking order.

**Priority:** P1 accessibility/export completeness  
**Type:** checked feature solves internal ordering but not assistive technology  
**Confidence:** high; implementation comment states the cut

What T106 now does well:

- stores a durable per-slide `rord` list of object IDs;
- resolves it once through `orderedIdx()`;
- uses it for build presets, figure numbers, Move matching and review text;
- preserves it through Python/JavaScript normalisation.

What it does not do:

- `orderedIdx()` explicitly says DOM order stays storage/z-order at
  `src/junoview/assets/js/deck/35-arranging.js:1892-1905`.
- `renderAnnots()` walks `s.annots` directly at
  `20-notes-and-tables.js:1788-1796`.
- PowerPoint export also walks `s.annots` directly at
  `60-saving-and-export.js:1358-1377`.
- Consequently a screen reader consuming rendered HTML, and PowerPoint's
  selection/reading order, can still follow stacking/storage order rather than
  the authored sequence.

Required change:

- separate visual stacking from semantic order instead of treating one array
  as both;
- render in authored semantic order while retaining visual `z-index`, or build
  an accessible ordered proxy that owns/describes the visual objects;
- emit PowerPoint shapes in authored reading order while preserving their
  visual stacking semantics through explicit z-order decisions;
- decide and test what PDF/print accessibility can actually preserve;
- add a browser accessibility-tree/DOM-order test and inspect the exported
  PowerPoint Selection Pane, not merely the internal `orderedIdx()` consumers.

### JVC-08 — native charts are valuable but not yet scientific/Office-class charts

> **Not yet addressed (2026-09-01)** — `chartParse` still coerces every non-
> finite value to zero, `chartSvg` still emits no accessible name,
> description or data alternative, and the accessibility lint still covers
> only images and flip books; the v1 cuts stand as recorded in T117's done
> note, with no new fix or decision since.

**Priority:** P1 accessibility/data correctness; P2 advanced charting  
**Type:** checked feature with explicit v1 cuts and additional omissions  
**Confidence:** high

What shipped is real: a `{k:'chart'}` model, bar/line/scatter/pie SVG drawing,
CSV editing, optional notebook-table provenance and real PowerPoint chart
parts. `TASKS.md:2149-2176` and `tests/test_charts.py` document/verify that
surface.

#### Explicit v1 cuts

`TASKS.md:2177-2181` and `assets/js/deck/47-charts.js:18-24` state:

- no per-series recolouring in the Junoview editor;
- no embedded workbook part, so PowerPoint's Edit Data sheet is absent;
- no stacking, 3D or secondary axes;
- a chart made from a deck table is a copied snapshot, not a live link; only a
  chart born from a referenced card refreshes.

#### Additional completeness gaps found in the implementation

- `chartSvg()` creates `<svg>` with a class/viewBox only
  (`47-charts.js:72-86`). It gives the chart no accessible `role`, `<title>`,
  `<desc>` or data-table alternative.
- The accessibility lint checks only `image` and `flip`, explicitly excluding
  chart objects (`50-review-and-overview.js:304-323`). A chart can therefore be
  completely opaque to a screen reader without a review finding.
- The chart model has title/legend/category/series data, but no x-axis title,
  y-axis title, units, log scale, error bars, confidence interval, reference
  line, data label or missing-value policy.
- `chartParse()` converts every non-finite value to numeric zero at
  `47-charts.js:38-44`. A typo, blank or non-numeric scientific value can become
  a real zero without warning, changing the claim the chart makes.
- Pie colours are taken directly from `CHART_PALETTE` rather than the stored
  series colour (`47-charts.js:92-120`), another sign that per-slice styling is
  not yet modelled.
- The current tests prove wiring, refresh and OOXML structure, but contain no
  chart accessibility or invalid-data case (`tests/test_charts.py`).

Required change, in order:

1. Preserve missing/invalid values as missing; never silently turn them into
   zero. Show cell-level errors in Edit Data and refuse an ambiguous apply.
2. Add accessible chart name/description and a tabular data alternative; teach
   Review to flag undecided chart descriptions.
3. Add axis titles/units and data labels—more important for scientific work
   than 3D effects.
4. Add in-editor series/slice colours and token support.
5. Add error bars, log scales, reference lines and uncertainty bands.
6. Decide whether deck-table charts should retain a table object ID and update
   live; if yes, make unlinking an explicit user action.
7. Add an embedded workbook part when full PowerPoint Edit Data support becomes
   a requirement.
8. Add stacking/secondary axes only after the semantic model can describe them
   consistently in Junoview and PowerPoint.

### JVC-09 — the review feature is still several checkers, not one complete report

## Definition of “implemented properly” for future tasks

A task should be checked only when:

1. the user-visible name matches what the feature actually does;
2. deliberate omissions are split into named follow-up tasks, not only buried
   in the checked task's prose;
3. the saved model is documented, normalised and validated;
4. editor, Present, static HTML/PDF and PowerPoint behaviour are either
   equivalent or the differences are disclosed at the decision point;
5. keyboard, screen-reader and reduced-motion behaviour are tested where
   relevant;
6. a failure cannot be reported as success;
7. a behavioural test proves the hard branch, not only that a string/function
   exists;
8. `TASKS.md`, help text and the current test-count/setup notes agree with the
   committed state.

That standard would let future agents tell the difference between “the v1 is
working”, “the feature is complete to its stated scope”, and “the application
now matches the full Office-class expectation”.
