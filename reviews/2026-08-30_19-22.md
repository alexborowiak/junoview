## Verdict

Junoview is already a substantial notebook-first presentation and poster tool.
It has many features that a superficial Office comparison would miss: notebook
provenance, code trails, self-contained card snapshots, presenter notes and
search, rehearsal timing, optional slides and named cuts, section navigation,
version-history branches, linked components, saved arrangements, design tokens,
custom text types, flip books, a design surface, PDF/HTML/PowerPoint export, a
PWA, and a live Jupyter widget.

It is **not currently a PowerPoint-and-Excel replacement**. The largest missing
domains are:

1. Native Excel workbook handling and spreadsheet behaviour.
2. PowerPoint import or round-trip fidelity.
3. Accessibility authoring metadata and an accessibility checker.
4. Native audio/video, recording, captions, and media-aware export.
5. Shared/cloud collaboration, which the backlog explicitly cuts.
6. True slide-master/layout inheritance and richer PowerPoint export.
7. Native charts/diagrams/data-bound objects rather than rendered notebook
   pictures.
8. A full authoring integration for JupyterLab.
9. End-to-end desktop support for the Markdown/LaTeX/CSV parsers that already
   exist.

The first product decision is therefore not “which button next?” It is whether
the intended product remains a focused notebook presentation system, or really
does take on workbook calculation, Office document interchange, hosted
collaboration, and media production. Those are separate subsystems, not ribbon
additions.

## How “missing” was judged

I used four statuses:

- **Absent** — no durable model and no complete UI/import/export path exists.
- **Partial** — a useful subset exists, but the name could reasonably imply
  more than the implementation delivers.
- **Cut** — explicitly excluded in `TASKS.md`; still missing relative to the
  PowerPoint/Excel ambition, but not an unfinished task.
- **Architectural boundary** — excluded by an invariant such as static rendering
  or stdlib-only core. Implementing it requires a product/architecture decision.

Positive evidence was preferred over search-by-absence. Where absence matters,
the strongest evidence is an exhaustive registry or schema:

- `src/junoview/notebook/sources.py:460-471` is the source-format registry.
- `src/junoview/notebook/deck_schema.py:57-198` and `DECK-FORMAT.md:31-136`
  enumerate the durable deck/slide/item kinds.
- `src/junoview/assets/js/pptx.js:558-714` enumerates every OOXML package part
  written by the PowerPoint exporter.
- `tests/test_deck_schema.py:153-217` checks that the documented schema and the
  loader do not drift.
- `tests/test_sources.py:225-323` pins source support and deliberately asserts
  that `.xlsx` is unsupported.

For the Office comparison, the baseline is current official Microsoft
documentation, not an imagined list of every menu entry:

- [Office Open XML package overview](https://learn.microsoft.com/en-us/office/open-xml/about-the-open-xml-sdk)
  describes presentation parts such as slide/notes/handout masters and
  spreadsheet parts such as worksheets, charts, and tables.
- [PowerPoint slide masters](https://support.microsoft.com/en-us/office/what-is-a-slide-master-in-powerpoint-b9abb2a0-7aef-4257-a14e-4329c904da54)
  establish inherited themes, layouts, fonts, effects, and placeholders as a

- [PowerPoint recording and video export](https://support.microsoft.com/en-us/office/turn-your-presentation-into-a-video-c140551f-cb37-4818-b5d4-3e30815c3e83)
  establishes narration, pointer movement, animation timing, and video export.
- [PowerPoint coauthoring](https://support.microsoft.com/en-us/office/work-together-on-powerpoint-presentations-0c30ee3f-8674-4f0e-97be-89cf2892a34d)
  establishes shared editing, comments, tasks, and presence.

  cover alt text, reading order, captions, and contrast.
- [Excel formulas](https://support.microsoft.com/en-us/office/overview-of-formulas-in-excel-ecfdc708-9162-49e8-b993-c311f47ca173),
  [PivotTables](https://support.microsoft.com/en-us/office/create-a-pivottable-to-analyze-worksheet-data-a9a84538-bfe9-40a9-a8e9-f99134456576),

## Detailed findings

### MF-01 — “Sources beyond Jupyter” is not end-to-end in the local app

> **Done (2026-09-01)** — T100, `a9b9b7c`. Every app-mode door (file
> browser, typed paths, drop, `/api/parse`) now opens any registered source,
> with the notebook-only routes kept strict as the review warned; T124
> (`2f3177e`) then labelled each tab's kind and stopped offering notebook-
> only doors on non-notebooks.

**Status:** partial and currently broken through normal desktop entry points  
**Priority:** P0 because the feature is presented as shipped

The producer layer is real:

- `src/junoview/notebook/sources.py:460-471` registers `.ipynb`, Markdown,
  Quarto, LaTeX, CSV, and TSV.
- `src/junoview/notebook/loader.py:29-40` dispatches a local `Path` through
  `doc_from_text()` by suffix.
- `tests/test_sources.py:273-293` proves direct file rendering for `.tex` and
  `.csv`.
- `tests/test_sources.py:296-306` proves the Pyodide web bridge can parse
  `.tex` and `.csv`.

The local-app doors remain notebook-only:

- `src/junoview/server/state.py:147-176`, `_list_dir()`, lists only directories,
  `.ipynb`, and `.junoview` files. Markdown, LaTeX, CSV, and TSV never appear.
- `src/junoview/server/routes.py:216-222`, `_resolve_nb_path()`, rejects every
  suffix except `.ipynb`.
- `src/junoview/server/routes.py:177-205`, `_open_nb()`, calls that rejecting
  resolver for local paths.
- `src/junoview/server/routes.py:346-359`, `_parse_nb()`, requires notebook
  JSON and calls `parse_notebook()` instead of `doc_from_text()`.
- `src/junoview/assets/js/app.js:5745-5756`, `submitOpenInput()`, sends only
  URLs, `.ipynb`, and deck files to `openPath()` in app mode.
- `src/junoview/assets/js/app.js:5796-5812`, the app-mode drop handler filters
  dropped source files to `/\.ipynb$/` and posts them as notebook JSON.
- In contrast, `src/junoview/assets/js/app.js:5325-5341` and `:5350-5374`
  use the complete `SRC_RE` path only for web/Pyodide mode.

This is more than a UX omission: the same file is supported by the CLI and web
build but rejected by the local app.

**Implementation seam for an agent**

1. Replace `_resolve_nb_path()` with a read-only `_resolve_source_path()` that
   checks `source_label()`/`SOURCE_SUFFIXES`; keep a stricter notebook-only
   resolver for note insertion and git-version APIs that truly require ipynb.
2. Make `_list_dir()` return a general `sources` list or include all registered
   suffixes in the existing notebook list with a type label.
3. Make `_open_nb()` call `load_doc()` for any registered local source.
4. Make `/api/parse` accept `{name, text}` and dispatch through
   `doc_from_text()`; retain `{nb}` compatibility if needed.
5. Route app-mode drop and typed paths through the same `SRC_RE` contract used
   by the web build.
6. Add end-to-end tests for local open, directory listing, typed path, and drop
   for at least `.md`, `.tex`, and `.csv`.

Do not grant note-writing, git notebook history, or `.ipynb` mutation to text
sources automatically. Those routes are correctly notebook-specific.

### MF-02 — Excel support is a static delimited-table preview, not a workbook

> **Done (2026-09-01)** — T113, `41b6865`. The architecture decision this
> finding demanded was made: Excel is in scope values-only, read by a stdlib
> zipfile+XML `parse_workbook` behind the new `doc_from_bytes` seam, one
> refreshable table card per sheet. Formulas, number formats, styles and
> merges are deliberately not read — the scope is recorded in the T113 note,
> so this is Excel import, not Excel parity.

**Status:** native Excel capability absent; CSV/TSV viewing partial  
**Priority:** P0 strategic

The limitation is explicit:

- `src/junoview/notebook/sources.py:21-30` calls delimited text the “Excel
  half” and explicitly excludes `.xlsx` and `openpyxl` to preserve the
  dependency-free/Pyodide architecture.
- `tests/test_sources.py:225-232` deliberately asserts
  `source_label("x.xlsx") == ""`.
- `pyproject.toml:11-13` and `ARCHITECTURE.md:7-8` promise a stdlib-only core.

What CSV/TSV support actually does:

- `src/junoview/notebook/sources.py:399-449`, `parse_table()`, creates one
  read-only dataset card for one file.
- The first row is always treated as headings (`:420-430`). There is no header
  detection or option.
- Cell values remain strings; there is no type system, dates, errors, formats,
  formulas, or recalculation.
- Only the first 500 data rows are rendered (`TABLE_ROW_CAP` at `:366`, slice
  at `:392`), although the caption honestly reports the total.
- There is no sheet/workbook structure, only one card.
- The deck’s native table is also intentionally simple:
  `DECK-FORMAT.md:120` says it contains “rows of plain strings, not HTML.”
  `src/junoview/notebook/deck_schema.py:195-196` confirms `table` is only an
  annotation kind with box geometry.

Therefore these Excel domains are wholly absent:

| Excel domain | Junoview evidence |
| --- | --- |
| `.xlsx`, `.xlsm`, `.xlsb`, `.xls`, `.ods` open/save | No suffix in `SOURCES`; explicit `.xlsx` negative test. |
| Multiple sheets/workbook navigation | No workbook or sheet object in `Document`, deck schema, or UI. |
| Editable cell grid/ranges | Dataset card is rendered HTML; deck table stores strings only. |
| Formula parser/calculation/dependency graph | Notebook provenance is Python AST dataflow, not spreadsheet calculation. No cell formula model exists. |
| Cell types, number/date formats, errors | CSV values remain strings; no cell metadata model. |
| Sort/filter/freeze panes | Document filters operate on notebook card categories, not table rows or columns. |
| Conditional formatting | No cell/range style-rule model. |
| Data validation/dropdowns | No cell validation model. |
| Named ranges/tables | No workbook namespace or range-address model. |
| Charts linked to cells | Figures are notebook output/images; no chart series/category model. |
| PivotTables/PivotCharts | No aggregation-field/layout model. |
| Power Query/connect-refresh pipeline | “Refresh figures” reloads notebook-backed frames; it is not a query/transform engine. |
| Data Model/relationships/Power Pivot | No table relationship or measure model. |
| What-if analysis, Goal Seek, Solver | No calculation engine. |
| Workbook protection/macros/add-ins | No corresponding model or runtime. |
| Excel comments/coauthoring/change history | Deck history is local snapshots, not cell-level collaboration. |

**Architecture decision required**

Adding `openpyxl` directly to the core conflicts with two load-bearing promises:
stdlib-only runtime and Pyodide parity. An agent should not “just add the
dependency.” Viable product choices are:

1. **Read-only optional producer:** an `excel` extra used only in the local
   Python app/CLI, with a clear degraded path in the web build. Lowest scope.
2. **Stdlib OOXML reader:** use `zipfile` + XML for values, shared strings,
   basic styles, formulas-as-source, and charts-as-metadata. Large but keeps the
   core promise; still not a calculation engine.
3. **Separate workbook subsystem:** new `src/junoview/workbook/` model and UI,
   with import/export adapters. This is the only path toward real Excel parity.
4. **Do not claim Excel parity:** keep CSV as a document source and phrase it
   that way.

**Minimum credible first milestone**

- Open `.xlsx` read-only with sheets, used ranges, values, basic formats, merged
  cells, formulas displayed, and a prominent “stored result/not recalculated”
  statement.
- Convert a selected range to a Junoview table or a notebook-ready CSV.
- Preserve workbook structure on a no-edit round trip or explicitly refuse to
  save `.xlsx`; never silently flatten it.
- Add fixture-based tests using OOXML packages with dates, formulas, shared
  strings, styles, merged cells, multiple sheets, and errors.

Anything smaller is useful, but should be named “Excel import” rather than
“Excel features.”

### MF-03 — There is no PowerPoint import or round-trip workflow

> **Deferred by decision (2026-09-01)** — T114, decided 2026-08-31: not now,
> but "come back for this for the full import at a later date" in the user's
> words. The T113 bytes seam and `DecompressionStream` are noted as half the
> plumbing when it is picked up, and the loss report on open stays non-
> negotiable.

**Status:** absent  
**Priority:** P0 strategic

Evidence:

- `src/junoview/assets/js/pptx.js:1-26` declares a PowerPoint writer.
- `src/junoview/assets/js/deck/60-saving-and-export.js:1519-1568` has only
  `exportDeckPptx()`/`pptxBuildAndSave()`.
- `src/junoview/assets/html/deck.html:132-136` exposes “Save as a PowerPoint.”
- The only deck importer, `importDeckText()` at
  `src/junoview/assets/js/deck/60-saving-and-export.js:1661-1713`, accepts
  Junoview JSON/polyglot HTML, not OOXML.
- No `.pptx`, `.pptm`, `.potx`, `.ppsx`, `.odp`, or legacy `.ppt` source suffix
  appears in `SOURCES`.
- `tests/test_pptx_export.py` covers only writing.

Consequences:

- Existing institutional/company templates cannot be opened or adopted.
- A deck exported to PowerPoint and edited there cannot come back.
- There is no migration path from existing PowerPoint libraries.
- Junoview cannot compare its output against the source deck structurally.

**Agent implementation seam**

A `.pptx` is a ZIP of related XML parts, not one XML file. A credible importer
needs a named boundary, preferably `src/junoview/presentation_ooxml/`, rather
than growing `notebook/sources.py`. It should:

1. Parse relationships and content types safely (no external entities).
2. Read slide order, page size, masters/layouts/themes, placeholders, notes,
   text runs, shapes, images, tables, hyperlinks, and supported animations.
3. Convert supported objects to Junoview’s durable schema.
4. Preserve unsupported parts or emit a detailed loss report; never silently
   claim round trip.
5. Keep import separate from the existing writer until shared OOXML primitives
   are actually stable.
6. Test with small hand-built packages and with PowerPoint-authored fixtures.

Macro-enabled formats should be read-only at first, with VBA preserved or
explicitly reported as dropped. Executing macros would be inappropriate.

### MF-04 — PowerPoint export is deliberately lossy beyond basic native shapes

> **Partly done (2026-09-01)** — most of the recommended order shipped: pre-
> export loss report and notebook tables (T109, `059caaf`), crops and
> fade/move transitions (T107, `9ae9b80`), speaker notes (T108, `a05f596`),
> hyperlinks and real `<p:timing>` builds verified in PowerPoint itself
> (T110, `b3f874e`), picture `descr` (T105, `fb11831`), and behavioural ZIP
> tests (T111, `5c63d60`). Still open: equations as OMML (recorded in T110
> as needing a second LaTeX front end) and real master/layout parts (T115's
> recorded cut).

**Status:** partial  
**Priority:** P1

What works well:

- Editable text boxes, pictures, real tables, shapes, connectors, freehand
  paths, page size, backgrounds, and a basic theme.
- `tests/test_pptx_export.py:16-166` pins those native representations.
- Flip books are expanded to real slides before export.

What is lost or flattened:

1. **Crops:** `pptxItems()` increments `note.cropped` for every crop at
   `src/junoview/assets/js/deck/60-saving-and-export.js:1388`; the completion
   toast says crops are not carried at `:1557-1558`.
2. **Equations:** MathJax/LaTeX is flattened to characters at `:1394-1401` and
   `:1483-1485`; the toast states this at `:1559-1562`.
3. **Notebook tables/rich reprs:** a frame containing a table is skipped at
   `:1477-1491`; only Junoview’s own annotation table becomes a native PPT table.
4. **Build animations:** `pptxBuildAndSave()` passes each slide only
   `{bg, items}` at `:1535-1545`. The writer receives no `anim` data.
5. **Slide transitions:** the same spec passes no `trans`; `pptx.js` writes no
   `<p:transition>` part.
6. **Speaker notes:** the writer emits `<p:notesSz>` at `pptx.js:658`, but no
   notes slide/notes master parts or relationships. `sl.notes`/`pres.notes` are
   not passed into `JunoPptx.build()`.
7. **Hyperlinks/actions:** slide relationships in `pptx.js:572-620` are only
   images and the slide layout. There is no hyperlink relationship or
   `hlinkClick` emission. The `hlink` strings at `:639` are theme colour-map
   names, not clickable links.
8. **Semantic alt text:** pictures are named, but the deck has no alt-text
   field and the writer emits no author-provided description.
9. **Components, anchors, history, provenance, private annotations, cuts:**
   these are Junoview semantics. Some are intentionally resolved or filtered
   before export and cannot round-trip from PowerPoint.
10. **Rich text detail:** export models largely box-level formatting. It does
    not preserve the full browser/Markdown run structure.

The UI is honest about three losses in
`src/junoview/assets/html/help.html:564-570`, but it does not enumerate notes,
links, builds, or transitions.

**Recommended work order**

1. Add a machine-readable export report object listing losses by slide/object,
   not only a transient toast count.
2. Carry rectangular picture crops using DrawingML `srcRect`.
3. Carry speaker notes with notes-slide and notes-master parts.
4. Carry hyperlinks/actions and their relationships.
5. Map `fade`/`move` conservatively to supported slide transitions; report
   anything approximated.
6. Map `appear`/`fade`/`rise`/`zoom` builds if a stable OOXML animation writer
   can be tested in real PowerPoint. Otherwise explicitly report them.
7. Consider Office MathML for equations; do not claim fidelity from plain text.

Each addition needs ZIP-part tests plus an out-of-band open/render test in real
PowerPoint or LibreOffice. String pins alone prove emitted text, not validity.

### MF-05 — Junoview templates are flattened arrangements, not true masters

> **Partly done (2026-09-01)** — T115, `f62ea2e`, addressed differently:
> live render-time master inheritance (`pres.masters`/`sl.mast`, background
> resolving slide > master > deck, component-backed furniture) with no
> stamped copies, so "restyle every wearer" works and no migration was
> needed. Still open: placeholder/prompt-text inheritance, master import
> from `.pptx`/`.potx`, and real per-master PPTX layout parts — export bakes
> the look, a recorded cut.

**Status:** partial  
**Priority:** P1

Junoview has strong adjacent features:

- Six built-in pane layouts in `DECK-FORMAT.md:89-100`.
- Saved arrangements and match-slide logic in
  `src/junoview/assets/js/deck/35-arranging.js:1102-1256`.
- Named text styles, design tokens, style sets, and the deck-wide design
  surface in `src/junoview/assets/js/deck/50-review-and-overview.js:1532-1826`.
- Reusable linked components in
  `src/junoview/assets/js/deck/40-captions-and-components.js:262-590`.

But the durable model says `lay` is only “the id of the slide template last
applied; annotations hold its actual geometry” (`DECK-FORMAT.md:76`). Applying
a layout copies/resolves geometry. There is no durable placeholder/master
inheritance tree whose later edit flows into child slides.

The PPTX writer further flattens this:

- Exactly one blank layout is written at `src/junoview/assets/js/pptx.js:624-630`.
- Exactly one master containing an empty shape tree is written at `:632-646`.
- All slides relate to that one layout at `:611-620`.

Missing master-level capabilities include:

- inherited placeholders and prompt text;
- multiple master/layout families;
- master objects and background graphics;
- theme font/colour/effect inheritance that survives PowerPoint editing;
- notes and handout masters;
- master/layout import from `.pptx`/`.potx`;
- propagation rules that distinguish “override here” from “inherit.”

Do not implement this by silently mutating every slide whenever a template
changes. The model needs explicit template identity, placeholder identity,
inheritance, per-slide overrides, and a migration for current flattened decks.
Components may supply reusable content, but they are not a replacement for
placeholder/layout inheritance.

### MF-06 — Accessibility authoring is mostly absent

### MF-13 — Markdown, LaTeX, and CSV producers are intentionally shallow

> **Partly done (2026-09-01)** — the shared asset-resolution defect is fixed
> and PDF figures become link cards (T101, `ebfa845`); Markdown gained front
> matter, pipe tables and inline links (T102, `90e875e`); LaTeX gained
> align, tabular and `\ref` (T103, `7fc6967`); source figures are now real
> figures downstream (T122, `6cd2cca`); and T113's `doc_from_bytes` opened
> the binary-producer seam this finding said was missing. Still open: the
> other formats (`.docx`, `.rst`, `.pdf`, `.html` and friends), the Markdown
> fallback for unknown suffixes, and bibliographies (recorded out of scope
> in T103).

**Status:** partial  
**Priority:** P2

The producers are small, dependency-free adapters, not full format engines.

Markdown limitations visible in `sources.py:119-209`:

- headings, fenced code, paragraphs, and image-only paragraphs are recognized;
- inline/multiple images, reference-style links/images, front matter, tables,
  footnotes, citations, includes, and executable Quarto semantics are not
  structurally parsed;
- an image receives the immediately following paragraph as its caption by
  heuristic;
- code fences become source cards but are never executed.

LaTeX limitations visible in `sources.py:216-360`:

- `_tex_plain()` explicitly says it is not a TeX engine (`:241-246`);
- only a small environment list is recognized (`:219-223`);
- citations/references are reduced to bracketed keys (`:252`), not resolved;
- tables are emitted as escaped raw LaTeX in `<pre>` (`:331-340`), not parsed;
- bibliography, packages, macros, includes, subfiles, cross-reference numbers,
  and actual Overleaf project structure are not modeled;
- no live Overleaf API exists by explicit design (`:28-30`).

Shared source problem:

- `_img_item()` preserves a relative path exactly (`sources.py:108-124`) but
  `load_doc()` does not pass the source directory into the `Document` or
  producer. The companion review demonstrates that exported/app pages therefore
  resolve local Markdown/LaTeX figures against the wrong location. LaTeX PDF
  figures are also passed to `<img>`, which browsers do not reliably render.

Other absent source formats include `.html`, `.pdf`, `.docx`, `.rst`, `.org`,
`.json`, `.parquet`, `.feather`, `.arrow`, `.ods`, `.pptx`, and project bundles.
Unknown suffixes fall back to Markdown (`sources.py:445-461`), which is generous
for README-like text but can misrepresent binary or structured data.

Each format should be added as a producer only when its fidelity and asset
resolution contract are explicit. Binary formats need a byte-oriented producer
interface; forcing them through `read_text()` is not viable.

## Cross-cutting rules for any implementation agent

- Read `ARCHITECTURE.md` and keep `Document` as the notebook/render seam.
- New disk writes belong under `src/junoview/server/`.
- Do not add runtime dependencies to core without an explicit architecture
  decision; Pyodide and the stdlib promise are affected.
- The deck editor is one shared IIFE assembled from 15 fragments. A new feature
  must cover normalization, persistence, undo/history, clone/copy, components,
  rendering, thumbnails, present mode, print, standalone HTML, PPTX, Python API,
  schema/docs, and tests as applicable.
- `docs/` is generated; never patch it directly.
- Preserve the user-confirmed UI invariants: ribbon rows do not wrap, and
  buttons use words plus icons rather than icon-only controls.
- Anything marked `[deck.js]` must not be implemented concurrently in two
  sessions.
- Add a real behavioural test where possible. Existing substring tests are
  useful contracts but do not prove complex OOXML, focus, media, or browser
  behaviour.
- Record deliberate omissions and approximation in the UI and export report;
  silent loss is worse than refusing a conversion.

## Bottom line

Junoview’s distinctive core is already stronger than “small PowerPoint clone”:
it can explain where a figure came from and keep a talk tied to executed
analysis. The best route to “PowerPoint and Excel and more” is not indiscriminate
feature copying. It is:

1. reliable distribution and complete source-opening paths;
2. accessible, durable semantics;
3. trustworthy Office import/export with explicit loss reporting;
4. a deliberate workbook subsystem if Excel is truly in scope; and
5. data-bound, provenance-preserving presentation objects that Office cannot
   offer as naturally.

Until those decisions and subsystems exist, Junoview should be described as a
notebook-first document, deck, and poster tool with PowerPoint export and CSV
viewing—not as having full PowerPoint or Excel feature parity.
